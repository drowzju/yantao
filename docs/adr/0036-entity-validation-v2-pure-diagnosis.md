# 实体校验 v2：回归纯体检

ADR-0035 把第四手势「实体校验 (validate)」立了起来，但 L1 落地后的真实体验暴露了管线层面的不满：**一张提议卡的批准率低、结果不可控**，根因被定位为单次 LLM 调用同时承担四个职责（找问题、建页、建链、提 todo）——模型注意力被稀释，每一类产出都不够精准；同时确定性预扫的结果（孤儿/失链）明明是零幻觉的图计算，却被塞回 prompt 让模型「包装」一遍，白白扩大幻觉面。参考同类项目 llm_wiki（`D:\code\llm_wiki`，Karpathy LLM-wiki 方法论的另一实现）的 lint 设计后，本 ADR 把 validate 重构为**纯体检**：确定性发现直出、模型只做窄职责语义诊断、修复按发现类型分工。本 ADR 取代 ADR-0035 的 L1 管线决策（决定 3/4 的 findings/creates 部分）；入口（决定 1 的 tab 内按钮）、预扫先行（决定 2）、统计与只弹卡（决定 6/7）、无口令（决定 8）继续有效。

事实基础（已核实）：现行管线在 `packages/client/ui-yantao/src/client/validate.ts`——`preScanOf`（:158）纯图计算孤儿与失链，但两份清单随后进入 `validatePrompt`（:185-237）充当模型研判的路标，模型在一个 JSON verdict 里同时输出 `findings/targets/creates/todos/questions` 五类东西（:55-62），`creates` 直接复用提炼的 `RefineCreateVerdict`（新实体页全文提案）。llm_wiki 的对照实现：结构性 lint 完全不过 LLM——`runStructuralLint`（`src/lib/lint.ts:157`）收集标题/出链/token 交给 Web Worker 跑 `computeStructuralLint`（`lint-structural-core.ts:102`），断链建议用 Levenshtein + bigram 打分；语义 lint 只查四种类型且规则硬编码在 prompt 里（`lint.ts:265-280`），喂的是每页 frontmatter + 前 500 字符的压缩预览（`lint.ts:244`）；输出走 `---LINT: type | severity | title---` 文本协议（`lint.ts:202`）；最关键的一道防御——模型报的 `missing-page` 会拿规范化标题集合（NFKC 折叠，`lint.ts:241-247`）二次核验，引用不存在页面的发现直接丢弃（`#537` 注释明确记载这是被误报咬过之后的补救）；修复与发现彻底分离，`lint-fixes.ts` 提供确定性修复函数（`appendWikilink` 幂等插链、`rewriteWikilinkTarget` 改写断链、`ensureBrokenLinkStub` 建占位页），LLM 只定位、代码执行修复、人审批。

决定：

1. **validate 回归纯体检**。`ValidateVerdict` 去掉 `creates[]`——校验不再提议新建实体页。「这里该有个实体 X」降级为一句 `missing` finding（纯展示），想真的建，人回到**提炼**手势去做——那里本来看着素材写新页，职责天然归它。体检的手只剩：发现（findings）与补链（targets 的 `links[]`）。
2. **确定性发现直出，不再过模型**。预扫的孤儿/失链清单不再作为「待模型处置的问题」进 prompt 包装，而是直接作为提议卡**确定性区块**的行（零 token、零幻觉）。模型调用的输入仍附送这两份清单（名字列表很便宜），但 prompt 明确告知：这些问题系统已发现并展示，**不需要复述**；模型只做清单之上的语义判断（例如两个孤儿其实是同一实体、失链原本想指向花名册里的谁）。
3. **窄职责诊断调用**。模型侧收敛为一次诊断调用，只输出 `findings`（语义类）+ `targets`（仅 `links[]`，补链动作）+ `questions`；`creates`/`todos` 从协议中移除（`todos` 留待远期 L2 再议）。诊断维度首版编入三项，规则逐条硬编码进 prompt：**过期**（`## 状态` 声称的事与点名实体近期内容冲突）、**矛盾**（实体内或点名实体之间互相打架的陈述）、**缺链机会**（明显相关但没有互链的实体对）。**冗余/疑似重复暂缓**——两两比对在单次调用里必然浅尝辄止，将来单独立按对窄任务再议。
4. **修复按发现类型分工**。失链：修复候选由**确定性代码**生成（对失链 target 做花名册相似度匹配给改写建议，风格同 llm_wiki 的 Levenshtein 打分），人勾选、代码执行改写；代码给不出高置信候选时该行退化为纯展示。孤儿：发现是代码的，修复（该跟谁建链）是语义判断，由模型的缺链机会维度产出、人批。内容类发现（过期/矛盾）v2 只呈 finding 不产修复动作——修复是内容生产，归提炼手势。
5. **代码侧防御核验**。模型 findings 的每个 `subject`、targets 的每个 `entity` 与 `links[].to`，先对花名册与链接图核验：解析不到的一律丢弃（宁缺毋滥，与 v2 解析器「空行丢弃」同一立场）。prompt 里「名单里没有的不要猜」从恳求升级为执法——模型说什么不算数，库里有什么才算数。
6. **提议卡分两区块**。确定性发现（预扫直出 + 代码修复候选）与模型发现（语义 findings + 补链动作）不混排：前者全信、后者逐条审。两类发现的信任等级不同，混排会让模型的不确定性污染确定性结果的信誉。
7. **输出协议不变**。仍是 JSON verdict + 一次 reask 重试 + v2 解析器（空行/未知 kind 丢弃）。llm_wiki 的 `---LINT---` 文本协议**不采纳**——那是它没有 JSON mode 下的权宜，我们有现成的解析与提议卡管道，没必要换。
8. **L2 重构想，另立 ADR**。ADR-0035 决定 5 的 L2（分批通读、解锁 edits/todos）建立在大管线之上，creates 移除与诊断窄化改变了它的前提；L2 的重新构想（含原预留的 ADR-0036 编号让位于本 ADR）待 v2 落地拿到真实误报/批准率数据后再议。

## 取舍台账——为控制牺牲的便利性

| # | 牺牲 | 换来 | 重开条件 |
|---|---|---|---|
| 1 | 校验不再顺手建页 | 体检语义纯粹；模型注意力全部花在判断上 | 「体检时顺手建页」的真实需求成真时立补充 ADR（预计不会——提炼手势更擅长） |
| 2 | 多一次跳转（发现缺实体 → 回提炼手势建） | 每个手势单一职责，卡片更短、批准更果断 | 跳转摩擦实测伤人时议「一键带上下文转提炼」 |
| 3 | 冗余/重复检测暂缓 | 不做注定浅尝辄止的两两比对 | 重复问题实测突出时立按对窄任务 ADR |
| 4 | 过期/矛盾发现无修复动作（纯展示） | 内容生产的爆炸半径不进体检 | 修复动作的确定性代码方案成熟时再解锁 |
| 5 | 诊断调用仍喂点名实体全文（8k 截断）而非压缩预览 | yantao 实体是长期沉淀的大文本，砍到预览会丢语义判断所需的上下文（llm_wiki 敢砍是因为它的页本是 LLM 生成的短文） | token 成本实测失控时分维度裁剪喂料 |

原因：

- **为什么一个发现一个信任等级、分区块呈现**：预扫是图计算，模型是概率猜测。ADR-0035 把两者揉在同一张卡的 findings 里，用户无法区分「机器算的」和「模型猜的」，不信任会传染——这是批准率低的直接推手之一。
- **为什么 creates 必须走**：校验和提炼抢同一件事（看素材、造新页），且校验场景下模型只见过 8k 截断的碎片，写出的新页质量必然劣于提炼手势拿着完整资源写的。同一个能力留两处入口，模型困惑、用户更困惑。
- **为什么防御核验是性价比最高的一项**：llm_wiki 的 `#537` 证明了「模型言之凿凿地引用不存在的东西」不是偶发而是常态。一次花名册集合查询就能把这类幻觉整类消灭，成本趋近于零。
- **为什么维度清单这么短**：llm_wiki 一次只查四种类型，每种的判据在 prompt 里写得具体而窄。宽泛的「帮我看看有什么问题」是误报之母；窄规则才有可辩护的产出。
- **为什么本 ADR 不附带任何代码改动**：管线重构（预扫直出、协议瘦身、核验层、双区块卡）是一次连贯施工，等实施 ADR/issue 拆票；先把设计共识定格。

后果：

- `packages/client/ui-yantao`（实施时）：`validate.ts` 的 `ValidateVerdict` 去 `creates`、`validatePrompt` 重写为诊断 prompt（附送预扫 + 勿复述声明 + 三维度规则）、新增 findings 核验层、`verdictToValidateProposal` 相应简化；失链修复候选的相似度匹配新增纯函数模块；Frame 提议卡分区块渲染。
- ADR-0035：决定 3/4 被 0036 取代（findings 直出、creates 移除、白名单收缩为只建链）；决定 5 的 L2 编号让位，重构想后另立。
- 文档同步：`docs/yantao/README.md` ADR 索引（本条）、`docs/yantao/TODO.md` 实体校验条目改写。设计背景与 llm_wiki 对照全文见 `.scratch/entity-validate-v2/analysis.md`。

落地注记（2026-09-29，五票施工完毕，`.scratch/entity-validate-v2/`）：决定 1/3——`ValidateVerdict` 去 `creates`/`todos`，`validatePrompt` 重写为诊断 prompt（预扫清单 + 勿复述声明 + 三维度窄规则），陈旧输出的 `creates`/`todos` 由解析层钉空。决定 2——预扫直出：孤儿条目与失链不再过模型，直接进卡的确定性区块。决定 4——失链修复候选落 `broken-link-suggest.ts` 纯函数模块（加权 Levenshtein + bigram Dice，阈值 0.74 对齐 llm_wiki、CJK 替换半价、包含关系 0.82、至多 3 候选），接入为 `edit-section` 动作行；流水小节的失链与小节外的失链降级为纯展示行（用户裁定），`类型:` 定位符整体替换为裸候选名（别名保留）。决定 5——`validate-verify.ts` 防御核验层：findings 的 `subject`、targets 的 `entity` 与 `links[].to` 对花名册/点名实体/失链目标核验，解析不到一律丢弃并计入 `filtered` 统计。决定 6——`Proposal` 增可选 `prescan` 子对象（orphans/findings/actions），与模型 `findings`/`actions` 类型上互斥；修复动作只居 `prescan.actions`（执行序前位由 applier 的 `[...prescan.actions, ...actions]` 拼接给出，不重复进模型数组），applier 与卡片各自按拼接序解析勾选索引，`Frame`/`applyProposal` 对外签名零改动；确定性区块平静样式、各侧全空整块隐藏。完成汇总口径同步：通报报「实体数 · 预扫 · 模型 · 滤除 · token · 耗时」。验证：ui-yantao 22 文件 428 例全绿，跨包回归（kb + controller）41 文件 801 例全绿；零新 RPC、零新 `kb_*` 工具。手动冒烟（启动工作台走完预扫→诊断→卡→批准补链）留待人验收。
