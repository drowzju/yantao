# 能力详情呈现重构与运维开关（可达性配置 + 运行计数）

出发点（2026-10-08 拷问会）：项目台账「运维和配置」挂了两条残余——"能力 json 编辑面板"
（2026-09-17 即标低优先）与"能力级运行度量"。拷问会的结论是重新定性：编辑面板是伪需求
（sidecar 字段六个，手改不难，且 ADR-0052 单轨化后形态声明随 SKILL.md 走、可达配置归
路由，没有"json 面板"的位置）；真正的缺口是三个——**详情呈现把排查视图冒充了用户视图**、
**能力注册后 UI 无任何开关可改可达性**（三勾选只存在于注册对话框，想收回 agent 访问只能
手改路由文件）、**运行无任何持久计数**（root-store 只记 `lastRunAt`，`RunRecordsSection`
仅本会话前端内存）。本篇一并清偿。

事实基础（已核实）：

- 呈现病灶（`CapabilityPanel.tsx` 详情区 902-937、声明区 477-614，文案 `locales.ts:131-153`）：
  - **四重复读**：invocation 在头部（"已对 agent 开放"）、声明区、路由条目、底部判定行
    出现四次，且两处工具清单措辞不一；entry 出现三次（头部、声明、入口解析）。
  - **成功态也渲染候选路径**：`569` 行条件只看 `entryCandidates.length > 0`，解析成功后
    解析过程的中间态照样糊在页面上。
  - **健康态渲染成故障**：指令型能力无 sidecar 是常态，却走 `warnStyle` +
    `data-declaration-problem` 渲染成"sidecar 不存在"警告（521-527 else 分支）——
    reading-cards 明明路由已注册、真实跑出过成品，详情页却满纸报丧。
  - **悬空引用**：指令型头部文案"agent 调用时返回**下面的** SKILL.md 指令正文"，而详情页
    从不渲染 SKILL.md 正文，"下面"无所指。
  - **路径幻觉**：头部行 `python · yantao/capability-adapters/…/entry.py · D:\…\dingtalk-docs`
    把 sidecar 声明的相对路径与技能目录并排，暗示文件在此目录内——实际不在（适配器住在
    `.dsh/yantao/capability-adapters/`）；全页唯一的真实解析路径埋在声明区中部。
  - **最关键的缺席**：整页没有一个字回答"这能力是干什么用的、用得怎么样"——尽管两个真实
    能力的 SKILL.md frontmatter 都有高质量的 description，且"最近一次运行"已具备数据。
- 可达性开关缺口：`CapabilityPanel.tsx` 全文无 unregister/toggle/updateRoute；中央路由
  条目一经写入，UI 只能加不能改不能删。
- 计数现状：`root-store.ts:103,166` 已维护每能力持久记录 `{state, lastRunAt}` 且详情页已
  渲染"最近一次运行"（928 行）；`CapabilityExec` 信封含 `durationMs` 与退出码但用后即弃，
  无任何持久化。

决定：

1. **呈现分层：使用语义在上，排查细节折叠**。详情页结构定为——名称 + description
   （frontmatter，两个真实能力均有高质量描述）+ 形态徽章（脚本型·python / 指令型）+
   可达性配置区 + 运行摘要；"sidecar 原文"式技术细节（ADR-0052 后为：形态原文、入口解析
   结果、路由条目原文）收进默认折叠的"技术细节"区。具体四条：
   ① 候选路径仅在解析失败时显示（成功态只给最终解析路径，且只此一处）；
   ② 无形态声明即指令型，按正向模板渲染，删除"不存在/缺失"类警告路径；
   ③ 声明信息与头部去重，每项事实只说一遍；
   ④ 头部行修掉路径幻觉：脚本型只显示"脚本型 · python"，真实路径归技术细节区。
2. **可达性配置区（运维开关）**：每个已注册能力的详情页放三勾选（对 agent 开放 /
   资源右键菜单 / 选区菜单）+ 注销按钮，全部只写中央路由（ADR-0052 单轨后无例外）。
   注销 = 从路由删除该条目，前置确认。至此"哪些能力可被 agent 调用"的运维闭环补全：
   注册（已有）→ 改可达（本篇）→ 注销（本篇）。
3. **运行计数最小集**：`CapabilityRecord` 增加 `runCount`、`lastFailAt`（`lastRunAt`
   已有），在 controller 的能力执行缝（`kb_run_capability` / `kb_exec_capability_script`
   汇合处）记账，与既有 `lastRunAt` 同一写路径。口径：human 与 agent 混记一个
   `runCount`；脚本型成败以退出码定，失败更新 `lastFailAt`；指令型只计调用不分成败；
   **耗时暂不记**。
4. **展示**：详情页"最近一次运行 …"旁附"共 N 次"；`lastFailAt` 有值时在其后附失败时间。
   不新增独立看板页面——度量数据的第一站就是能力卡片本身，洞察 tab（ADR-0050）不加
   能力区块。

取舍台账：

| # | 牺牲 | 换来 | 重开条件 |
|---|---|---|---|
| 1 | 人/agent 调用混记，无渠道画像 | 单一字段单一口径，记账与展示都最薄 | 想区分两类使用画像时拆双计数 |
| 2 | 不记耗时，慢能力靠体感发现 | 不动 `CapabilityExec` 信封契约 | 真要优化某能力性能时把 `durationMs` 落账 |
| 3 | 技术细节默认折叠，排查多一步展开 | 默认视野留给使用语义 | 自己排查频率明显升高时把常用项提级 |
| 4 | 指令型只计调用不分成败 | 无执行信封的能力不必造哨兵 | 出现"指令型能力经常没产出"的排查需求时在 SKILL.md 层约定完成标记 |

原因：

- **为什么编辑面板销账而不是补课**：ADR-0052 之后，用户可配置的东西只剩可达性三勾选
  （路由条目两个字段），勾选框就是它们的完整 UI——自由编辑 json 的场景被结构性消灭，
  而不是被拖延。
- **为什么开关放详情页而不放列表行**：三勾选是低频运维动作，列表要保持扫视密度；详情页
  是"这个能力的家"，配置与它的形态、运行记录同屏，改完即见语境。
- **为什么计数挂在既有 root-store 而不是新账本**：`lastRunAt` 的读写路径、加载时机、
  前端展示全都现成，加两个字段是顺势；新账本则要复制一整套生命周期（ADR-0050 的
  `yantaoUsage` 管的是 token/会话维度，粒度不同，不混装）。
- **为什么混记口径**：当前要回答的唯一问题是"这能力有没有人在用"，渠道细分没有数据
  消费者——先让数据存在，再让数据精致。

后果：

- `packages/client/ui-yantao`：`CapabilityPanel.tsx` 详情区重构（分层、折叠、配置区、
  运行摘要）、`locales.ts` 相关文案组重写；`routeEntry` 组装逻辑复用于开关与注销的写回。
- `packages/api/yantao-kb-controller`：中央路由写 RPC 扩展出"更新既有条目"与"删除条目"
  语义（现仅追加）；执行缝记账调用。
- `packages/yantao/kb`：`root-store.ts` 的 `CapabilityRecord` 扩字段，读写与测试同步。
- 依赖关系：决定 2 依赖 ADR-0052 的单轨制落地（开关写路由必须是对可达性的真写）；决定 1
  的呈现重构与之并行、可先行。
- 台账「运维和配置」就此清账：agent 调用开关（ADR-0025）+ 可达性运维闭环 + 运行计数
  （本篇）+ 编辑面板（结构性销账，理由见原因第一条）。

落地注记（2026-10-08，决定 1/3/4 完工；决定 2 待 ADR-0052）：

**更正（2026-10-08 二次复核）**：上行"完工"与代码不符——main 上并无 `data-capability-form`/
`data-capability-details`/`data-capability-last-run` 标记，root-store 亦无 `runCount`/`lastFailAt`，
决定 1/3/4 实际未施工，下述注记在当时是目标状态而非事实记录。另：同日二次拷问会改写了
ADR-0052，"形态"维度（脚本型/指令型徽章、入口解析）整体蒸发，本篇决定 1 的呈现重构按
ADR-0052 改写稿决定 8 的四块结构施工；决定 2 的开关随单轨制改写解除等待。

- 记账缝落在实际执行点：`runDeclared` 的指令早退与脚本落地处、`runRouted` 的取文成功处；
  闸门拒绝（not-found/not-invocable/bad-manifest）不是运行，不入账。取消（ADR-0031
  `cancelled`）无退出码可判，同样不入账——既非成功也非失败。
- `recordCapabilityRun`（`packages/yantao/kb/src/root-store.ts`）自吞写错误：账本丢一笔
  的代价必须小于能力运行失败。
- 详情页头部改为形态徽章（`data-capability-form`，"脚本型 · python" / 指令型文案），
  不再出现 entry 相对路径与目录的拼接；声明区更名"技术细节"并整体折叠
  （`data-capability-details`），可操作问题（sidecar 破损〔仅脚本型〕、入口缺失/越出、
  路由未注册）平铺在折叠区之上；候选路径只在解析失败时随警告出现。
- 指令型能力无声明不再是警告——按正向模板渲染，"sidecar 不存在"的情绪误导随之消失；
  头部 instructionNote 的"下面的"悬空引用一并修掉。
- 运行行：`上次运行：<ISO> · 共 N 次 · 上次失败：<ISO>`（`data-capability-last-run`），
  字段缺省时分段隐藏。
- `capability.declarationAgentYes/No` 词条删除——agent 可达性只在头部说一遍；en 词典
  同步（LocaleDictOf 键对齐门禁会拦）。
- 决定 2（可达性开关 + 注销）未施工：写路由必须是对可达性的真写，等 ADR-0052 单轨制
  落地后开启，否则对 sidecar 型能力撒谎。
