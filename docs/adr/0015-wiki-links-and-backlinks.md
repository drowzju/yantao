# `[[双链]]` 与反向链接

决定：

1. **链接写法**：`[[名字]]`，可选 `[[类型:名字]]`（消歧）与 `[[名字|显示名]]`（别名）。**不允许链到 `resources/`**——
   原件不是实体、没有 `type:` 拼写，也不该被这样寻址。
2. **解析规则复用已有的 `type:name` 定位**（单复数、中英文冒号、大小写不敏感；会议支持日期前缀回退），
   并且**必须落在唯一一个实体文件上**：零个或多个命中一律算未解析。未解析的链接**保留 `[[…]]` 原样**，
   不悄悄变成死链——"没连上"要看得见。
3. **解析与扫描都在宿主**：新增 `yantaoKb.links(path)`，返回 `{ outgoing, incoming }`。
   宿主本来就会在树加载时把每个实体文件的全文读一遍，所以反向链接几乎是副产品；
   放到客户端则是"每个文件一次往返"，还要自己管缓存失效。
4. **渲染**：`MarkdownText` 只接受 http(s)/mailto 目标，`kb:` 或相对路径会被它直接丢掉，
   所以已解析的链接渲染到一个**保留域名 `https://kb.invalid/<path>`**（RFC 2606，永不解析），
   点击由阅读视图接住并打开文件，不会真的跳走。未解析的保持原样文本。
5. **反向链接面板**：有入链时顶部给「反向链接 N」，列出来源文件（并标出它写的 target），点击打开该文件。
6. **点击链接/入链都是打开一个新的文件 tab**（走现有的 `openFile`），不替换当前 tab。

原因：

- **为什么必须唯一命中才跳转**：KB 里重名是常态（周会每周一个、项目与领域可能同名）。
  静默挑第一个会让人以为连对了而实际上连错；宁可显示成未解析，让人补一个 `类型:`。
- **为什么链路放在宿主而不是前端扫描**：一次往返 vs N 次往返只是表面——真正的理由是
  "一个名字指哪个文件" 是宿主规则（locator、日期会议、去重），前端复制一份必然漂移。
- **为什么用 `kb.invalid` 而不是改渲染器**：`MarkdownText` 没有扩展钩子（ADR-0014 已查），
  为双链去自研渲染器要重造表格、代码高亮、公式。一个保留域名换一个可点击的链接，比那便宜得多；
  代价是链接的 href 不好看，且依赖"点击被接住"——若接不住会跳到一个必然打不开的地址（已用保留域兜底，不会外泄数据）。
- **为什么未解析保留方括号**：这是给人的反馈。渲染成灰色的死链看着像连上了，保留 `[[…]]` 才像"这条没生效"。
- **为什么链路不影响写入**：链接只是文本。勾选任务框（ADR-0014 v2）仍然改的是源码行，
  链接解析不参与写路径，因此不会和保存前比对打架。

后果：

- `yantaoKb` Remote 多一个方法 `links(path)`——**改 Remote 契约意味着客户端 face 必须重编**
  （`pnpm run build:lib`），否则浏览器拿到旧方法表。
- 扫描是 O(文件数 × 文件大小) 的一次读：个人 KB（几百个小 md）无感；KB 长到上万文件时要改成常驻索引，
  那时应该连 TODO 里 deferred 的 FTS/backlinks 索引一起做，而不是单独优化这里。
- 链接只在 `entities/` 内成立：`resources/` 下的影子笔记如果有 `[[…]]`，解析不出实体就是未解析（符合预期）。
- 代码块里的 `[[…]]` 不算链接（解析与扫描都跳过围栏），避免示例文本变成链接。
- 未做：链接的自动补全（在编辑器里打 `[[` 弹候选）、未解析链接的集中清单、重命名实体时改写引用
  （都会动到写路径，属于另一个功能）。
