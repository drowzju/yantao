# 任务统一视图与取消

工作台有三类后台执行：提炼管线（ADR-0029/0030 的专用会话）、邮件分析（ADR-0019 的分块判定循环）、脚本能力运行（ADR-0021/0023 的控制器子进程）。它们有两个同源的缺口：(1) **发了收不回**——提炼一旦入队只能等到人类终点，邮件分析一口气跑完全部 chunk，能力子进程跑到超时为止，中途没有任何止损手段；(2) **散落不可见**——三个执行的进行时分别活在提炼卡、邮件面板和提示条里，没有一个地方能回答「现在都在跑什么、跑到哪了、哪些能停」。本 ADR 补齐这两件事：先给三类执行统一的取消语义，再把它们的执行情况聚合进中央栏一个常驻的「任务」tab。发起入口不动——任务照旧从各处分散发起，不做统一发射台。

事实基础（已核实）：三个执行的进行时状态本来就全部活在 React 里——提炼队列是 Frame 的 state（ADR-0030 决定 7），邮件分析是 `mailRun` store 的 state（含 `phase`/`progress`/`error`/`hint`），能力运行是 Frame 的 running 位；dsh 的 `session/cancel` 通道已在生成的客户端 face 里，此前无人调用；typert 宿主方法按位置传参，尾部追加可选参数对既有调用方零破坏；控制器 `runCapability` 的子进程经 spawn 拉起，kill 即死；UI 是这三类执行的唯一发起者，agent 经 `kb_run_capability` 的调用不经过前端，控制器侧无从上报；中央栏 tab 的持久化（ADR-0012）只针对文件 tab，常驻 tab 不在其中。

决定：

1. **取消语义按执行器各定义，共同立场是「尽力而为、落地的成果保留」**。提炼：中止信号触发 `session/cancel` 结束当前专用会话，队列随取消清空，问题对话框一并放弃；已出的提议卡保留待人裁。邮件分析：跑完当前 chunk 后不再发起新请求，已落地的判定保留；**水位线不动**——下次分析从头再判（宁重勿漏，半截水印比重判更危险）；取消与错误分开记账（state 增 `cancelled` 见证位）。能力：中止即杀子进程，运行以 `cancelled` 类失败告终；**工作台刷新同样视为杀死任务**——不追踪孤儿进程（台账 #4）。
2. **AbortSignal 尾参约定**：可中止的宿主方法在签名末尾追加可选 `AbortSignal`（`capabilityRun(args, signal?)`）；typert 校验容忍省略，旧调用方零破坏。中止的见证是调用者手里的那个 signal 本身——控制器不另设取消簿记，signal 随运行生灭。
3. **任务 tab 常驻**：中央栏第二个永久 tab「任务」（与「对话」并列），tab 上带运行数徽标；永不关闭、不持久化。
4. **前端聚合，零后端任务模型**：Frame 持有 `taskRows` 状态并提供 `taskBegin`/`taskPatch`/`taskEnd` 三个回调，三个执行 Owner（提炼队列、mailRun、capabilityRun 包装）各自上报生命周期；纯模块 `task-view.ts` 负责排序、计数与时长格式化。零新 RPC、零新工具、wire 不动。
5. **行模型**：一行 = 一次执行；标题「动作+对象」（提炼「提炼〈实体〉」/「归入〈资源〉」、邮件「邮件分析（N 封）」、能力「能力〈名〉」），列依次为阶段（排队中/创建会话/分析中/正在写入/执行中…）、进展（如「已判 X/Y 封」）、耗时（`mm:ss`，运行中每秒走）、取消（仅运行中有）、查看（跳转——提炼去会话 tab，其余展开左栏并切到能力页签）。扁平单列：运行中置顶按开始先后，其次待确认，已结束按结束倒序沉底。
6. **仅前端记忆**：列表只记本会话——运行中 + 本次已结束（完成/取消/失败）；刷新即失，不持久化（台账 #1）。
7. **已记录局限：agent 发起的执行不可见**。agent 经 `kb_run_capability` 等工具自行发起的执行不经过前端，视图只收「工作台自己启动的执行」——这是信任边界的自然结果（工具层的执行以会话流水为账本），不是遗漏（台账 #2）。

## 取舍台账——为控制牺牲的便利性

| # | 牺牲 | 换来 | 重开条件 |
|---|---|---|---|
| 1 | 仅前端记忆，刷新即失 | 零后端任务模型、零新 RPC，行为完全可预测 | 需要跨会话/跨刷新的任务历史时引入持久化任务簿记 |
| 2 | agent 发起的执行不可见 | 信任边界不动，视图不必与工具层对账 | agent 任务多到需要监督时给工具层加执行上报 |
| 3 | 邮件取消不动水位线，下次从头重判 | 落地判定保留，且不会出现半截水印 | 重判成本不可接受时分块记水位 |
| 4 | 能力取消 = 杀子进程，无优雅退出 | 取消即时生效，不需要清理协议 | 脚本需要清理钩子时约定退出协议 |
| 5 | 提炼取消清空整个队列 | 一键止损，扫目录提炼随时可弃 | 需要「只取消当前、保留后续」时拆分语义 |

原因：

- **为什么取消先行于 tab**：取消是能力缺口（发了收不回），tab 只是观察窗口；先有可停的东西，再谈看得见。
- **为什么前端聚合而不立后端任务模型**：三个执行的进行时状态本来就活在 React 里，后端再立一份必然漂移；单人单机没有第二个客户端要对账，前端聚合是最小正确解。
- **为什么 signal 是尾参**：typert 方法按位置传参，尾部追加可选参数是对旧调用方零破坏的唯一形态；见证放调用者手里，控制器不需要「谁取消了」的簿记。
- **为什么「工作台前端是任务宿主」**：桌面壳（ADR-0016）已是这些执行的宿主进程，前端死了执行本来就没有观众；后端任务簿记是为多客户端准备的，我们没有多客户端。「刷新 = 杀任务」不是缺陷，是这个立场的推论。
- **为什么徽标**：运行中的任务不该等人点开 tab 才被看见。

- **零新工具、零新 RPC**：`kb_*` 保持十一、`yantaoKb` RPC 保持二十一（`capabilityRun` 只添了尾参，个数不变）；生成的 API 目录随签名更新（`api-catalog.ts` 与子系统页，已重跑生成器）；AGENTS.md 硬规则 2 不动。

落地注记二（2026-09-21，试用反馈两则）：

1. **邮件读取也是一行**。首用发现读取阶段在任务 tab 里不可见——只有点了「分析」才出行，而读取同样是工作台发起的执行。修正：Frame 把面板传入的 `mailFetch` 包成 `bookedMailFetch`，读取以「读取邮件」一行呈现（读取中 → 已读 N 封 / 已取消 / 失败），`MailFetcher` 与 `fetchMail` 同样吃 AbortSignal 尾参，行上的取消中止的是读取自己的 signal——与分析行的 `mailRun.cancel()` 按 id 区分，两个生命周期不重叠（分析从读取的结果起步）。
2. **「待确认」不是行的终点**。首用发现确认写入后行永远停在「提议待确认」：镜像 effect 在提议卡打开时清掉了行 id，后续 applying/idle 两拍拿不到 id 就返回。修正：打开卡片只把行挂起（`waiting`），id 留着，确认写入走「正在写入 → 已写入 N 项」、关掉卡片走「已忽略」，仍是同一行。
