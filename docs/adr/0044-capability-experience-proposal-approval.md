# 能力经验回流记忆：提案-批准制（kb_propose_memory 与提炼手势）

出发点（2026-10-01 裁决）：无论 UI 手势触发能力还是会话内调用能力，运行中学到的坑与经验都应最终总结提炼成凝练文字，**经人批准后**沉淀为行为记忆。这是 ADR-0032 记忆系统的写侧补全——读侧（注入）与信任声明（ADR-0043 决定 4）已成，唯写侧缺席。

事实基础：

- **agent 无记忆写面**：kb_* 工具无一触及 `.dsh/yantao/memory/`；`kb_write_resource` 锁 `resources/` 首段（ADR-0028），`.dsh/` 机制内部不可写（ADR-0042）；`memoryAdd/Delete` 是 UI 人道 RPC（`yantaoKb` remote），agent 没有 RPC 通道。
- **经验的三条去路全是死胡同**：会话结束蒸发；写实体流水/章节（`kb_append_log`/`kb_edit_section`）——实体作用域的历史，下次调用该能力不会回注；落 `resources/` 新文件（creation-only）——之后无人再读。实证：dingtalk-docs 的四条能力记忆（代理兜底/key 即密码/jsonml 判空/快照 diff）全是整编日人肉录入。
- **记忆是杠杆最高的持久注入面**：全局记忆进系统提示动态小节（每回合读盘），能力记忆挂 `kb_run_capability` 返回尾部【行为记忆·宿主转交】块——都是常设指令。今日可信全系于一件事：每一条都是人批准的（注入头明文承诺）。给 agent 直写 = 信任反转：能力输出 → agent 转写 → 记忆 → 未来所有运行，投毒链持久化。ADR-0042 事故证明 agent 对注入的警惕是对的；写侧需要与 ADR-0043 读侧声明镜像的裁决，而不是顺手开洞。
- **两表面不对称**：会话面有 agent 在场（读完结果即可提炼）；UI 手势面（`capabilityRun`）是宿主直接执行脚本，无 agent 在场——提炼者需要另行供给。

决定：

1. **提案-批准制**：两个表面的经验走同一条管道——提炼成凝练文字 → 提案队列 → 人批准 → 行为记忆。三方 skill 零改动，改动限于我们的包与 `.dsh/` 契约。提案队列**永不注入**：毒性输出至多躺在队列里等人过目；「人在以往运行中批准沉淀」的注入头措辞继续为真。
2. **`kb_propose_memory(scope, text)`**：新增 kb 工具（ctx.tools 层，与 kb_run_capability/kb_exec_capability_script 同层），唯一的 agent 记忆写面——只进提案队列。工具描述承载两条礼仪：学到非显然的东西（坑/绕过/环境怪癖/用户纠正）才提，通常在任务收尾；提案不生效，人批准才沉淀。scope 校验沿用 `assertMemoryScope`（`global` 或能力名形状段）——非能力专属的工作台级坑同样可提为 global。
3. **提案队列**：`.dsh/yantao/memory/proposals/<scope>.md`，与记忆文件同构（行式条目、id = sha1、日期戳），每条加来源注记（表面：会话 / UI 运行摘要），转正时剥离来源、只落凝练正文。挂起软帽 20 条：满时拒绝新提案并提示人先处理队列——队列语义与记忆不同，积压要有痛感，不无声堆积。
4. **提案预检**：提案时对照该 scope 现有记忆与在途提案，文本重复即拒绝（与 `appendMemoryEntry` 的 duplicate-memory 同款），agent 就地得知「已存在」，不制造噪音。
5. **会话面即时批准**：agent 提案后会话内渲染轻量批准卡片（原文 + 目标作用域，批/丢两键；视觉纪律沿提案卡体系，ADR-0038）；当场批准即时转正，漏批/忽略的落记忆视图兜底。
6. **UI 面手动提炼**：能力 tab 运行记录旁「提炼经验」按钮（2026-10-01 裁决：手动）→ 宿主拉起一次性 headless agent（与会话 agent 同一 kb 工具面，UI 直驱专用会话先例 ADR-0029），输入 = 该次运行信封（命令/退出码/时长/stdout/stderr 尾）+ 该能力现有记忆（防重复提议），指示其产出 0~3 条凝练候选经 `kb_propose_memory` 落队。平淡运行零开销，成本与意图对齐。
7. **批准转正**：记忆视图「待批准」区统一陈列全部在途提案（含来源供人判断），批准时可改判目标作用域（默认来源 scope），转正复用 `appendMemoryEntry`——去重、软帽、行式格式整套白得；丢弃即移除。人道 RPC 三件套：memoryProposalList/Approve/Discard。

取舍台账：

| # | 牺牲 | 换来 | 重开条件 |
|---|---|---|---|
| 1 | 经验生效有人工延迟（批准前不注入） | 注入面 100% 人批，ADR-0032 定位与注入头承诺保真 | 用户主动要求 agent 直写时——须先重审持久投毒链 |
| 2 | 提案队列是要养的收件箱，积压满 20 拒新案 | 队列永不无声膨胀 | 软帽值不合理时调 |
| 3 | UI 面提炼每次烧一次模型调用（手动触发） | 成本人控、平淡运行零开销 | 提炼需求高频常态化时考虑失败自动触发 |
| 4 | 会话内多一类卡片形态 | 反馈回路最短，agent 当场知结果 | 提案洪水时收紧工具描述礼仪 |
| 5 | headless 提炼者依赖模型网关在线 | 两表面共用同一支笔与同一工具面 | 网关不可用时报错即可，不做本地降级硬造 |

原因：

- **为什么提案-批准而不是直写**：记忆是常设指令级注入面，直写即信任反转——ADR-0032 的定位（「人批准沉淀的行为规则」）是整套机制的信任根基，ADR-0043 决定 4 刚把读信任固化为架构事实（一次声明），写侧开洞等于自我否定。提案制把信任锚放在人的一次批准动作上，与「安装即授权」（ADR-0021/0043）同构：agent 有提名权，决定权在人。这也是全库一贯协作边界（邮件删除、实体归档的 agent 纯文本提名权，ADR-0034/0041）在记忆域的投影。
- **为什么不落 resources/ 收件箱**：creation-only 语义下每条经验一个新文件，碎片化且无人再读；提案需要「可列举、可批准、可丢弃」的队列语义，属机制内部状态，住 `.dsh/`。resources 方案仅剩零施工过渡价值（改一行 CAPABILITY_ENVIRONMENT_NOTE 即可启用），正式形态是本 ADR 的提案队列。
- **为什么 UI 面手动而不是自动**：UI 运行大多平淡，自动 = 每次烧模型调用；失败固然教训最浓，但人未必每次都想沉淀。手动按钮把成本与意图对齐（2026-10-01 裁决），信任锚位置与决定 1 一致。
- **为什么会话内即时卡片**：agent 提案的当下人就在会话里，当场批是最短反馈回路；记忆视图兜底保证不丢（2026-10-01 裁决）。
- **为什么队列与记忆同构**：行式 markdown 的 hand-edit 存活、sha1 id 稳定、解析退化不崩溃——memory.ts 的既有性质整套继承；转正 = 移动一条，不建第二套存储。

后果：

- `packages/yantao/kb`：memory.ts 旁新增 proposals.ts（队列读写、预检、软帽）；index.ts 注册 `kb_propose_memory`（工具总数 +1）。
- `packages/api/yantao-kb-controller`：`yantaoKb` remote 增 memoryProposalList/Approve/Discard；Approve 转正调 `appendMemoryEntry`（重复即报已存在）；headless 提炼编排（宿主侧拉起一次性 agent 的入口，复用既有会话构造）。
- `packages/client/ui-yantao`：能力 tab 运行记录「提炼经验」按钮与提炼中状态；记忆视图「待批准」区；会话内 `kb_propose_memory` 调用结果渲染为批准卡片；typert/remotes 产物再生成。
- AGENTS.md 硬规则 2 的工具枚举同步（`kb_propose_memory` 入列，注明「只进提案队列、永不注入」）。
- 文档：packages/yantao/CONTEXT.md 词条增补（提案）；《能力整编手册》补记忆回流一节；ADR-0032 以本 ADR 为写侧权威；docs/yantao/README.md 索引入列。
- 测试：队列读写/预检/软帽、工具注册与描述礼仪、RPC 三件套、转正去重联动、提炼编排信封输入、卡片渲染，随施工补齐。
