# 提议流水线的分批暂存与动作代生成

出发点（2026-10-20 调度实测）：一次邮件解析跑完 29 封，工具结果总量从基线的 137KB 降到 57KB，
压缩却从 10 轮涨到 16 轮（24.4 分钟，占墙钟 67%），并出现三类可归因的浪费：

- **32 项动作全被闸门剔除**：模型把取数结果的 40 位指纹 `id` 抄进了 `entryId` 槽位，另有两处
  形状错误（`type` 写成 `entityType`、`entityType` 写成 `entityPath`）。回执 4KB、三十条同义诊断。
- **15 次白跑取数**：扫描结果本来带全部 `entryId`（slim 行也带），但压缩把原始结果吞掉了，
  模型只能逐封用 2 秒窗重取，约 10 分钟。
- **重复组装**：29 封的分析一直挂在上下文里，被拒后整批重来，又起草了一次 32 项 JSON。

事实基础：

- 提议收件箱（ADR-0047）本来就是外部存储，`kb_propose_actions` 只入队——缺的不是存储，是
  「分批写入、收尾合并」的中间落点。
- exec 桥已按运行键下发 `CAPABILITY_RUN_LEDGER`（2026-10-20 去重批次），同一把运行钥匙
  可以再下发一个暂存路径。
- 闸门（ADR-0055）逐项容错的口径不变：坏项点名剔除、好项照常入队；要改的是回执的呈现密度。

决定：

1. **运行级暂存文件**（`.dsh/yantao/proposal-staging/<run>.json`，运行键=会话 id，与去重账本同级）：
   `kb_propose_actions({draft:true})` 只把本批合格动作并入暂存、不建卡；缺省调用（draft 缺席）
   先读暂存、与本次 actions 合并、一次校验、**一张卡**，入队成功后清空暂存。一跑一卡（2026-10-10）不变。
   暂存 fail-open（坏文件当空）、合并写 + 原子替换（脚本与工具交替写不互相覆盖）、
   同一封按 `kind+entryId` 合并（修复轮的新行胜）、24 小时老化清理。
2. **脚本代生成动作**：邮件能力新增 `scripts/stage_actions.py`，收 `{delete:[id…], archive:[{id,summary}…],
   since, until}`，自己从 Outlook 解析 `entryId`/`sender`/`subject` 并直接写暂存。
   模型只给 id，`entryId` 不再经过上下文——指纹误填这一类错误从机制上消失。
   脚本只在会话运行里可用（`CAPABILITY_RUN_STAGING` 缺席即拒），人通道行为不变。
3. **回执按因合并**：`groupDiagnostics` 把三十条同义诊断压成一行（`第 4–11、14–26 项「delete-mails」…`），
   4KB → 数百字符；单条与异因诊断保持原文。
4. **工具描述瘦身（有界）**：压缩最长的几段描述与参数说明（控制器 20 个工具 9.1KB → 8.8KB），
   但不做按会话过滤工具——`ToolDefinition` 没有可见性谓词，那是上游接缝，本篇记为非目标；
   结构性的 8K token 固定开销要等上游支持按会话裁剪工具面再谈。
5. **agent 通道取数缺省 slim（2026-10-20 实测）**：`entry.py` 在 agent 信封下默认不取正文
   （回执 `slim: true`、`body` 为空串），人通道不变，调用方显式 `slim` 优先。同一批 29 封
   带正文首取 319 秒、slim 只要 8 秒——分诊本来只需要元数据，正文按需单封取。
   同时 `stage_actions.py` 增加 `--help` 自述：让 agent 查接口而不是读源码/试 import，
   因为每一步都要付一轮压缩。

后果：

- 一跑一卡与信任锚不动：暂存不是卡，人批准仍是唯一的写入授权。
- 分批的上下文只记「暂存了几项、覆盖到哪个时间」，动作明细在文件里，压缩吞不掉。
- 收尾提交是幂等的：同一批重跑按 entryId 覆盖，不会在卡上出现两遍。
- 暂存残留（进程崩溃）由 24 小时清理兜底；即使漏到第二天，也只是一张没人批准的空卡候选，
  不影响取数与水位。

台账：

1. 上游若支持按会话裁剪工具面，把「邮件运行只暴露 8 个工具」列为下一批候选（预计再省 8–10KB schema）。
2. `stage_actions.py` 目前只覆盖删除/归档；若待办与实体动作也变多，再扩它的计划形状。
