# 读书项目与资源入库（拖放入库 + 废除影子笔记配对）

资源是知识库的入口，但此前入库只有一条路：agent 调 `kb_register_resource` 复制文件并强制生成影子笔记——
而影子笔记 agent 自己写不了、没有机制保证存在、也不能被 `[[…]]` 指向（ADR-0015），是个三不靠的空壳。
本 ADR 给资源一条人的入口（拖放），并给"读一本书"这样的深加工一个正式的载体（读书项目）。

决定：

1. **拖放入库**：任意文件拖到资源栏即登记——复制进 `resources/`（净化文件名、重名即拒，语义同
   `kb_register_resource`，但走浏览器传内容而非绝对路径）。**不再自动生成影子笔记**：废除"每个资源
   必须配一个同名 `.md`"的强制配对。
2. **影子笔记降级为邮件路径的实现细节**：`type: resource` 笔记格式只保留在邮件留存这一处——
   那里的资源生来就是 markdown，笔记即资源本身（`resources/<标题>.md`，`source: mail`）。
   已有知识库里的旧影子笔记**不做迁移**：它们就是普通的 `.md` 资源文件，留着不碍事。
3. **读书项目是普通 `project` 实体**，frontmatter 加一个 `source:` 字段存资源路径
   （如 `source: resources/三体.epub`）。**有 `source:` 字段的 project 即读书项目**——这是判别器，
   不新增实体类型。标题约定 `读书-《书名》`（书名取自文件名，创建弹窗里可改）。
   双链仍然不允许指向 `resources/`（ADR-0015 不动），项目指回书靠 `source:` 字段，UI 渲染成可点跳转。
4. **创建流程是应用级弹窗，不是 agent 提问**：资源行右键「创建读书项目」→ 确认框（书名 +
   「是否需要我读取书籍内容为你整理大纲？」）→ 点「是」则建项目（`source:` 自动填）并直接触发一次
   agent 运行。这一步的答案是可预知的二选一，不值得动用 agent 问询机制。
5. **文本抽取是惰性的**：拖入时只复制；建项目确认后才抽取。方式是 **Python 脚本**（拷进仓库自己
   维护，先例是 ADR-0019 的 `read_outlook.py`——把解析库的坑挡在 Node 进程之外），支持
   pdf / epub / doc / docx / ppt / pptx / txt / md。缓存进知识库根旁的 `.yantao/extracts/`
   （不进树、不污染 `resources/` 的"原样不改写"），抽取状态（格式、分块数）记在缓存目录
   自描述的元数据里，**不进项目的流水**——机器簿记不冒充知识。
6. **抽取失败是明确失败**：扫描版无文字层、加密、损坏——报错告知"此书无法文本抽取"，读书流程
   终止，项目保留、状态区写明原因。**v1 不做 OCR**，不做降级方案（不假装成功）。
7. **agent 用新的分页读工具读原文**（如 `kb_read_resource`：按偏移/分块返回抽取文本）——一本书
   几十万字，一次性塞不进上下文。读书流程的编排靠提示词，不写死代码。
8. **产物落点**：大纲写进读书项目的 `## 状态`（agent 可写区，ADR-0010），阅读过程记 `## 流水`。
9. **领域关联走提议卡**：读完书，agent 结束回合时输出 MailReview 式提议卡（ADR-0019 的两段式：
   agent 提议 → 人确认 → 下一轮执行）——建议关联一个或多个已有领域，或提议创建新领域
   （「根据书籍方向，是否创建『认知科学』领域？」）。确认后 agent 把 `[[领域:名字]]` 写进状态区
   （反向链接由 ADR-0015 自动算），新建领域调既有的 `kb_create_entity`。
   **除分页读外零新工具**，信任边界不动（建领域有人工确认卡着）。
   阻塞式 ask-user（回合内挂起等点击）不在本 ADR 范围，值得做也是独立的后续 ADR。
10. **UI 收尾**：资源只读横幅的「编辑其影子笔记」改为「创建读书项目」（不留死按钮）。
11. **分期**：一期 = 本 ADR 全部（含 pdf/epub/doc/docx/ppt/pptx 抽取）；OCR、阻塞式 ask-user、
    非书资源的通用"加工项目"留待后续。

原因：

- **为什么废除影子笔记**：它对 agent 是只读摆设（七个 `kb_*` 工具都碰不到它）、对人不强制
  （手动丢进 `resources/` 的文件没有它，也没有校验）、对双链不可见（links.ts 禁止指向
  `resources/`）。它的真实价值只有两条——二进制资源的文本面孔和来源元数据——而这两条在
  读书方案里分别由读书项目和"哑资源"承担。PARA 的本意就是：资源是哑的原材料，思考发生在
  实体层。想加工一本 pdf？建读书项目，产物住项目里，不住资源旁边。
- **为什么惰性抽取**：Q11 已接受"没人加工的资源是哑的"。登记即抽会让每次拖入都背着解析库的
  代价和失败面，而收益（可检索的文本）要到建项目才用得上。
- **为什么 Python 脚本**：pdf/epub/office 文档的解析库在 Python 生态最全；Node 侧没有能打的
  同类品，且 ADR-0019 已确立"解析跑子进程、JSON 走 stdout"的模式，照抄即可。
- **为什么弹窗是应用级的**：这一步的问题是 UI 知道全部上下文（文件名）的二选一，让 agent 转述
  一遍纯属浪费一轮。真正的 agent 问询需求在领域建议那步，那里用提议卡已经够了。
- **为什么提议卡而不是阻塞式**：MailReview 已验证"agent 提议 → 人勾选 → 下一轮执行"可行，
  不用动 host 的回合模型。阻塞式体验更连贯但改动深，不该搭在这趟车上。

后果：

- `registerResource` 退化为纯复制（不再写影子笔记）；拖放走其内容上传变体（新 RPC）。
- 新 RPC 意味着 `pnpm run build:lib` + `pnpm run gen-cordis-catalog` 必须跑，controller 的
  README 对（RPC 表 + "N unary methods"句）和 `docs/subsystems/yantao.md` 随实现同步。
- 词汇表删「影子笔记」条目、KB_README（`templates.ts` 常量）改文案——**随代码落地一起改**，
  不提前（文档不能先于行为）。
- `.yantao/` 目录加入知识库树的不显示名单（与 `sessions/` 同待遇）。
- 邮件路径不动：它写的资源笔记本来就是"资源即笔记"，与新世界相容。
- 未做：OCR（扫描版）、阻塞式 ask-user、非书资源的通用加工项目、读书进度的断点续读。
