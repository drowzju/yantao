# 提炼闭环 v1（资源归入与实体提炼）

TODO 里挂了两条同源的功能：**把资源文件拖到实体上**触发一次分析（相关则更新实体、无关不处理），以及给实体「整理」能力（对照新模板调整、追加新发现、补双向链接）。词汇表早已给这条流程定了名——**提炼 (Refine)：人触发 → agent 提议（建议卡）→ 人批准**，「整理」恰是 `_Avoid_` 里的禁用同义词；deferred 清单里的「提炼闭环 v1」就是它们合起来的样子。此前做不了，缺的是 agent 自主读资源这一环；ADR-0028 把环补上了（`kb_read_resource` + `@` 目录展开），基础设施恰好齐了：提议卡是唯一勾选写入窗口（ADR-0021）、`kb_edit_section` 可改实体任意区段（ADR-0026）、双链机器全套在案（ADR-0015）。

本 ADR 把两条合并成**一条管线、一张卡、一套确认语义**：两个手势（拖资源到实体、右键提炼实体）只是同一管线的两个触发源。

事实基础（已核实）：邮件分析是**客户端直驱**的先例——`mail-analysis.ts` 经 session Remote 建会话、命名、`jsonRound`（要 JSON 裁决、不可解析重问一次），客户端把裁决解析进 Proposal（`analysisToProposal`），全程不新增 RPC；提议卡是纯客户端产物，六类动作里**没有整段替换**（`write-state` 只往 `## 状态` 插一行），`applyProposal` 走 UI 通道整文件写入（`insertIntoSection`）；`kb_edit_section` 的锚点缺失/重复是硬错误、**不重建**（`locateSection`）——老实体缺新模板区段时 agent 侧工具加不上，只有 UI 通道整文件写能补；ADR-0026 定死「模板只影响新建，存量不迁移」（取舍台账 #6）、frontmatter 不可被 agent 写、流水对一切写者 append-only；拖放目标今天只有 intake rail（`Workbench.tsx` 的 `onDrop` → `registerResource`），实体行只有右键菜单、没有任何 drag/drop 处理；实体行右键已把实体路径递给手势层。

决定：

1. **一条管线，一张卡：UI 直驱专用会话，不碰 pre-step、不声明能力**。两个触发都由客户端（ui-yantao）仿 `mail-analysis.ts` 驱动一次**专用会话**：读实体与资源全文 → 组提示词 → `jsonRound` 要 JSON 裁决（不可解析重问一次）→ 解析为 Proposal → 弹提议卡。**不是 ADR-0025 pre-step 管线的触发源**——不合成聊天消息、不进能力目录、agent 不能自行调用；`/提炼` 不存在。确认语义只有一种：提议卡勾选。会话照邮件先例**保留并命名**（「提炼 <实体名>」），判断可回读；会话里不写库，分析只提议。
2. **两个手势**：
   - **归入**：把资源文件拖到左列实体树行上。库内拖（资源树行 → 实体行）直接分析；**系统拖入**（资源管理器 → 实体行）先走 intake rail 同款 `registerResource` 落入 `resources/` 再分析——「拖入入库」与「归入实体」合成一个手势。一次只接受一个文件，多文件拒绝并提示。相关性由同一趟会话裁决：无关 → toast 显示理由，不弹卡、不写流水、不留痕。
   - **提炼**：实体行右键「提炼」。对照该类型当前模板（用户模板优先、内置回落，读法与建实体同源）检查区段结构，按自己的理解追加新发现，建议与其它实体的 `[[双链]]`。
3. **提议卡新增 `edit-section` 动作**（第七类）：`{ path, section, before, after, why }`——整段替换预览，目标区段**不存在时视为新建**（这正是「对照模板调整」的字面意义，只有 UI 通道做得到）。边界三条：目标区段是 `流水` → applyProposal 直接拒绝（与 `replaceSection` 的 `log-append-only` 铁律同构，UI 通道不成为绕行口）；**frontmatter 永不进提议**（ADR-0026 决定 2 不破）；确认提炼/归入的写入时，提议固定附一条 `append-log` 行（人勾选才写，与其它动作同权）。链接不设新动作类型——`[[…]]` 内联在 `after` 正文里随段落一起预览、一起落盘（`create-link` 的「状态区插一行」形态不适合成片链接建议）。
4. **落盘语义：重读、重定位、逐动作失败标红**。从生成提议到人勾选之间实体可能被手动改过——`applyProposal` 处理 `edit-section` 时**落盘前重读文件、重新定位区段**再替换；锚点丢失/重复 → 该行动作失败并在卡上标红，其余动作照常。绝不按生成时的快照整文件覆盖——UI 通道也不吞人手改动。
5. **边界与判据**：
   - **逐实体、人手触发的 opt-in**。模板对照实质是逐实体迁移：这是 ADR-0026 取舍台账 #6 重开条件（「用户手工调教个别老实体」）的兑现形态——仅人工逐个触发，**不做批量迁移**，ADR-0026「存量不迁移」的立场不变。
   - 提示词给洞见落点的判据，agent 放进最合适的**既有区段**（影响目标的进 `目标`、可执行的进 `下一步`、事实性的进 `状态`）；区段缺失时由 `edit-section` 补建。不新增 `## 发现` 之类区段——模板区段各有语义，另设会稀释模板。
   - 二进制资源（NUL 判定，ADR-0028）内容不可读：归入分析只凭文件名与路径判断相关性，如实告知模型「内容不可读」。不转码、不摘要——那是能力脚本的事（ADR-0028 台账 #1）。
   - 资源内容注入的体积防线照抄 ADR-0028 现状（32k 截断、二进制占位），实体全文照读。

## 取舍台账——为控制牺牲的便利性

| # | 牺牲 | 换来 | 重开条件 |
|---|---|---|---|
| 1 | 不注册能力：不进 `/` 目录、agent 不可调、聊天里 `/提炼` 不存在 | 确认语义只有一张卡一种；UI 手势不需要 `invocation` 门控 | 聊天触发提炼成为真实需求时声明指令型能力（届时聊天侧产物形态另议） |
| 2 | 与 pre-step 管线无关：手势不过会话输入、不合成消息 | 复用邮件分析先例，零新 RPC、零新工具 | 无——这是选择不是缺陷 |
| 3 | 二进制资源只凭文件名判断 | 资源永不改写与「不注乱码」立场不破（ADR-0028） | 「读 PDF/图片归入」成为真实需求时走能力脚本抽取 |
| 4 | 单文件 v1，多文件拖入拒绝并提示 | 一张卡一次裁决，不爆炸 | 批量归入成为日常时加队列 |
| 5 | 提议过期逐动作失败标红，不自动重试 | 人手改动永不被吞 | 失败频繁成为困扰时做「重新提炼」一键 |
| 6 | 提炼不碰 frontmatter、不批量迁移存量 | schema 层与 ADR-0026 立场不破 | 同 ADR-0026 台账 #1、#6 的重开条件 |

原因：

- **为什么走邮件模式而不是让聊天会话发提议卡**：任意会话可发卡是一条新管线（会话产物如何回流 UI、如何防重复弹卡都是新语义）；邮件分析已经验证了「专用会话 + JSON 裁决 + 客户端解析」这条最短路径，且它的会话留痕恰好满足审计——判断可回读，写入仍过卡。普通聊天会话里 agent 依旧只能经 `kb_*` 工具在对话里干活，两条通道互不混淆。
- **为什么现在做**：三个前提在九天内相继落地——提议卡成为唯一勾选写入窗口（09-14）、`kb_edit_section` 放开区段编辑（09-16）、`kb_read_resource` 让 agent 自主读资源（09-17）。缺任何一环，「agent 分析实体并提议改写」都只是人肉搬运。
- **为什么 `edit-section` 落在卡片而不是扩 `kb_edit_section`**：缺区段补建只有整文件写做得到（工具层锚点缺失即硬错误是有意设计——agent 不该无声改结构）；而「补建」发生在人勾选之后，由 UI 通道执行，边界不破。卡片动作集补上整段替换后，邮件/归入/提炼三种产物共用同一套动作词汇。
- **为什么无关不留痕**：原话即「无关则不需处理」；流水记一条「看过、无关」是审计噪音。真要回溯，会话还在列表里。
- **为什么系统拖入也收**：`registerResource` 是现成的，「下载个 PDF 拖到项目上」是最自然的真实场景；只收库内拖反而逼人先拖到 rail 再从树里拖一次。

后果：

- `packages/client/ui-yantao` 增量：`proposal.ts` 增 `edit-section` 动作类型；`proposal-apply.ts` 增重读-重定位-替换与流水拒绝；新增提炼模块（仿 `mail-analysis.ts`：会话驱动 + 提示词 + JSON 解析）；`Workbench.tsx` 实体行成为 drop 目标（库内拖 + 系统拖入先 `registerResource`）、`RowMenu` 增「提炼」项；`Frame.tsx` 挂载提炼提议卡。
- **零新工具、零新 RPC**：`kb_*` 工具数保持十一、`yantaoKb` RPC 保持二十一；controller README 与 `gen-cordis-catalog` 不漂移。`AGENTS.md` 硬规则 2 不动。
- 会话经 session Remote 直驱（mail 先例），会话命名「提炼 <实体名>」；`jsonRound`/`turn-answer.ts` 复用。
- 文档同步：`docs/yantao/README.md` ADR 索引（本条）、`docs/yantao/TODO.md`（deferred 的「提炼闭环 v1」移入 next 并指向本 ADR）、`packages/yantao/CONTEXT.md` 增「归入 (Intake)」词条（随实现）；ADR-0026 台账 #6 加「已由 ADR-0029 重开（逐实体人工触发形态）」注记（随实现）。
- 未做：批量归入、二进制资源内容分析、聊天侧 `/提炼`、提炼建议的 diff 并排视图（v1 用 before/after 文本块）、自动定时提炼。
