# 提议管线可靠性：溯源校验、差异可视与执行对账

出发点（2026-10-13 周报流水事故复盘裁决）：当晚 21:00 调度「公共周报刷新到实体」接连暴露两类
结构性缺陷。其一，agent 提炼张冠李戴——袁文茂实体的流水整段写成了周我要周报的内容，人抽查
才发现，且事后派出的同源模型自查 agent 同样放过该条；其二，19 条 append-log 提议被人批准后
**零写入**却结算为 approved（client bundle 构建于 resolveEntity 修复之前，locator 逐条解析
失败被 skip，skip 不阻断结算），卡片滚出视野后不留任何痕迹。复盘裁决：模型自查不可依赖
（同源模型犯同构错误），凡确定性的、近乎零成本的防线必须由代码把守；人审是信任锚，但锚点
必须看得见东西。次日补充讨论（2026-10-14）进一步裁决：溯源从「自愿透传」升级为「资源提炼
语境下强制」，并增补读取闭合校验补上「遗漏」方向的检查——记录是供料，闭合校验才是牙齿。
本篇立案，覆盖提炼→入队→人审→执行→结算全链。

事实基础（已核实）：

- **卡片上看不到将落地的内容**：append-log 行的主文本是 `entityName`、详情是 `reason`
  （`ProposalCard.tsx:217/:265`），`text` 本身不上卡——批准者物理上无从发现内容错误。
  而 ADR-0038 决定 9 对 append-section 已有正确裁决：「detail 就是将落地的 text」。
- **diff 基建现成**：skill-rewrite 已有折叠式行 diff（`lineDiff`、del/add/same 着色、
  `proposal.diffView` 开关，`ProposalCard.tsx:312-346`，ADR-0054）。
- **快照先例**：edit-section 携带 `before`（模型所见原文）上卡展示（`proposal.ts:139`）。
- **结算语义二元且有静默缺口**：`confirmInboxEntry` 先 apply 后 settle；逐条 try/catch，
  单条失败标记后跳过、不阻断；全部失败仍 settle approved（`Frame.tsx:977-1009`）。
  per-action 结果无处留存。
- **applier 无入笔前预检**：locator 解析失败是在逐条执行时才暴露的——若先整批验一遍，
  本次事故（旧 bundle 解析不了 `project:`/`person:` 前缀）会在落第一笔前就被拦下。
- **逐项容错先例**：ADR-0055 修订已确立 `partitionProposedActions` 合格项/坏项分离、
  坏项诊断随工具结果带回的模式。
- **词汇表孪生**：动作 kinds/字段表在 controller 与客户端各持一份，parity 测试钉漂移
  （ADR-0055 决定 3）。
- **事件日志可作读取见证**：ADR-0055 决定 5 已让调度器在 run 结束后扫描事件日志检出行内的
  工具调用——同一份日志里也含本轮全部 `kb_read_resource` 调用及其路径参数。即「这轮实际
  读过哪些文件」有机器可查的账本，溯源核对不必只信模型自报。
- **JSONL 台账惯例**：workspace-runs.json 环形截断（ADR-0056 决定 6）确立了运行史与
  定义分家的先例。

决定：

1. **溯源字段进数据结构，资源提炼语境下强制**：append-log（及 write-state、create-link 等
   实体落点动作）增加 `sourcePath`（提炼来源的资源路径）与可选 `sourceQuote`（原文摘句）。
   强制不含工具层——工具只知道来源调度 id（ADR-0055 决定 4 的 `source`），不知道该调度是否
   资源提炼——而在调度约定层：凡约定声明为「资源提炼」的调度（周报刷新、邮件归档等），约定
   行明文「每条陈述事实的实体动作必须携带 sourcePath」；违例由校验 B（决定 2）在 run 收尾
   点名，逐项上卡警告并计入通知——**不做整批退回**：整单制已被 ADR-0055 修订废除（27 项
   大单整单拒修三轮的事故应激），缺溯源的项照逐项容错点名，不连坐合格项。豁免条款同样明文：
   纯决策类动作（add-todo、create-entity 命名等）不要求溯源——不给豁免，模型会对无法溯源
   的动作编造来源应付，比缺席更糟。与 ADR-0055 决定 4 的卡级 `source`/`sourceName` 并存
   不冲突：卡级答「这张卡从哪个调度来」，动作级答「这条内容从哪个资源来」。沿 edit-section
   `before` 的快照先例，不算破例；孪生词汇表两侧同步，parity 测试扩样。
2. **入队双校验（机械，非模型）**：
   - **校验 A（内容重叠，入队时）**：controller 校验器对带 `sourcePath` 的项做专名核对——
     从 `text` 抽取专名/编号/数字（项目代号、型号、百分比等 token），在其声称的来源文件内容
     中求重叠，命中率低于阈值即判坏项、走 ADR-0055 的 dropped 通道当轮带回模型。拦「内容与
     出处不符」。校验成本一次 grep。
   - **校验 B（读取闭合，run 结束扫描时）**：调度器本就要扫事件日志检出行内工具调用
     （ADR-0055 决定 5），同一份扫描顺带取出本轮全部 `kb_read_resource` 路径，做双向闭合：
     正向——每条 action 的 `sourcePath` 必须 ∈ 实际读取集合（引用了没读过的文件 = 伪证，
     纯精确匹配零误杀）；反向——读取集合中每个资源要么被至少一条 action 引用，要么在
     `note` 中声明「本期无要点」（读了没写 = 遗漏，梁雄高漏掉智能采集头条项即此类）。闭合
     违例不阻塞入队（工具执行时拿不到会话事件，ToolRunContext 无 sessionId），在调度扫描点
     以警告附着到卡片（走既有 ProposalHighlight 通道）并计入通知，人审批准前可见。
   - 两条互补：A 管「写了但内容对不上出处」，B 正向管「出处是编的」、反向管「读了但漏写」。
     袁文茂张冠李戴会被 A 拦（内容 token 全命中的是周我要的文件）；伪证与遗漏只有 B 能见。
     决定 1 的强制也由 B 兜底执法：缺 `sourcePath` 的项使其来源资源在反向闭合中无着落而被
     点名——强制、伪证、遗漏三个问题共用同一次扫描执法。
3. **卡片显示落地文本（追认通则）**：append-log / write-state 行的 detail 从 `reason` 改为
   将落地的 `text`（ADR-0038 决定 9 追认为全体实体动作的通则），`reason` 收进次级展示。
4. **append-log 折叠 diff**：行展开后用现成 `lineDiff` 渲染「流水尾部上下文 + 绿色新增行」。
   appendLog 拼装是确定性的（`` `${content}\n- ${stamp} ${note}` ``），卡片展开时读一次
   实体当前流水尾部即可算出精确预览；有 `sourcePath` 时行尾附来源链接，可点开与提炼并排对照。
5. **结算三分 + 逐项留痕**：卡片结算状态从二元扩为 `approved / approved-with-errors / failed`；
   per-action 结果数组 `{index, ok, error}` 存入收件箱行（卡片展示的权威数据）。另设
   **apply-ledger**：`<kbRoot>/.dsh/yantao/apply-ledger.jsonl`，每次结算追加一行审计记录
   （proposalId、decidedAt、逐项结果、摘要）——审计真相独立于实体文件与收件箱（两者都可能
   被清理或恰好在写入失败时不可用），环形截断沿 workspace-runs 惯例。
6. **零写入硬闸 + 入笔前 dry-run（全灭拦截，个案容错）**：整批应用前先做一轮 locator
   可达性预检，按命中分档——**全部不可达 → 整批一字不落**，保持 pending 并报因（含「此批
   提议产生于旧版客户端，请重启后重试」的针对性提示）：全灭几乎必然是环境性根因，逐条 skip
   只会掩盖它；**部分不可达 → 跳过坏项、逐项留痕（决定 5），按 approved-with-errors 响亮
   结算**——个案失败不连坐好项，沿 ADR-0037 决定 7「一封失败不拖垮整批」的执行层逐项容错
   先例。零写入静默从此不存在：全灭拦在落笔前，个案败在账面上。
7. **失败可见性与重试**：已处理卡不消失——折叠展示逐项错误列表 + 「重试失败项」按钮
   （只重跑失败子集，生成新的结算记录）；结算时经既有 `setCapabilityNotice` 通道发汇总通知；
   调度无人值守场景由提议 tab 徽标计数兜底。**不往实体流水写失败标记**——写实体失败时实体
   恰恰写不进去，且系统事件混入 append-only 流水污染语义；账本是唯一可靠落点。

分期：P0 = 决定 5/6（结算语义与预检，本次事故的直接教训）；P1 = 决定 1/2/3（溯源强制、双
校验与落地文本可见）；P2 = 决定 4 的 diff 视图、决定 7 的重试与通知细化。

取舍台账：

| # | 牺牲 | 换来 | 重开条件 |
|---|---|---|---|
| 1 | 强制溯源只覆盖调度约定声明的「资源提炼」语境，会话内即兴提炼不受约束 | 执法成本落在已有的约定行与事件扫描上，零新信任机制；伪造出处被读取闭合的正向校验精确戳穿 | 会话内即兴提炼出现实际事故 → 给 ToolRunContext 补 sessionId 使工具层也能强制 |
| 2 | token 重叠是启发式，改写幅度大的正当提炼可能被误杀 | 确定性拦下张冠李戴级错误，成本一次 grep | 误杀两例以上 → 阈值下调或改嵌入相似度 |
| 3 | 读取闭合的反向检查依赖模型如实声明「本期无要点」，故意漏报难辨 | 遗漏类错误从无声变为有账可查（读过却无着落的资源被点名） | 反向误报成灾 → 只保留正向伪证检查 |
| 4 | 卡片 diff 预览需展开时读一次实体（RPC 往返） | 预览与真实落盘字节一致，不靠模型快照 | 实测卡顿时改缓存流水尾部 |
| 5 | 全灭才整批拦截，个案失败仍会以 approved-with-errors 落账（好项落、坏项留痕） | 静默 skip 变响亮的提前失败或账面记录，且不冤枉个案 | 实践证明部分失败同样高发环境根因 → 收紧为任一不可达即整批拦截 |
| 6 | 又一个 JSONL 文件（apply-ledger） | 审计真相独立存活，跨重启可对账 | ——（体积环形截断，无增长之忧） |

原因：

- **为什么不指望模型自查**：本次事故中人审、agent 自查两道模型防线先后放过同一条错误；
  事故后全量复核靠的是「逐人对源机械比对」。结论：凡可用代码判定的，不交给模型判断。
- **为什么溯源要强制而不是自愿**：来源记录本身也是模型生成的元陈述，自愿形态下错绑与漏绑
  都无声；强制逐条申报迫使模型在生成时当场对齐内容与出处（归因错误多发于「事后批量归档」
  的松散形态，本次 19 条正是如此），更重要的是它把不可证的叙述变成可机械证伪的命题——
  记录是供料，校验 A/B 才是牙齿，缺记录则两校皆空转。
- **为什么校验 B 可能**：ADR-0055 决定 5 已在 run 结束后扫描事件日志，「本轮读过什么」
  本就有机器账本。读取闭合把溯源核对从「信模型自报」升级为「模型自报 × 读取见证交叉验证」，
  且是唯一能抓「遗漏」方向的检查（内容校验只对已写的条目生效，漏写的条目 A 永远看不见）。
- **为什么校验在 controller 入队时**：与 ADR-0055 同理——此时数据还在模型手里，坏项诊断
  当轮可见、当轮可修；拖到批准后修复要多一整轮，拖到执行后就成了数据事故。校验 B 晚一步
  （run 结束扫描点）是 ToolRunContext 无 sessionId 的既有限制，警告上卡已足够把违规暴露
  在人审之前。
- **为什么显示落地文本排 P1 之首**：人审是整条管线的信任锚，锚点上看不见东西，后面所有
  校验都只是减少坏项到达率，看得见才让人审真正有否决力。ADR-0038 已为 append-section 立
  同规，本篇只是补齐同类的课。
- **为什么账本不写在实体里**：append-only 流水的语义是「这个实体发生了什么」，不是「系统
  对这个实体做过什么」；且写入失败场景下实体恰恰不可写。审计记录的消费者是人复盘与机器
  对账，独立文件才是它的家。
