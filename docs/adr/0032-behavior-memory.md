# 记忆系统:行为规则层

yantao 至今没有独立的记忆机制。`memory.md` section 里那句「知识库是这个工作台的唯一长期记忆」是纪律口号,不是机制:事实性的沉淀由实体与流水承担(提炼闭环 ADR-0029/0030 负责「是什么」),但**「怎么做」层面的规则与偏好**——「处理邮件时同类邮件直接提示删除」「新建项目应尝试关联 area」「此人的事别归入 area」——没有居所,每次纠正都从零开始,agent 下次照样犯。本 ADR 定义记忆系统:记忆 = 影响 agent 行为方式的规则与偏好,与实体知识划清边界。设计来源是 2026-09-23 的讨论纪要([memory.md](../yantao/memory.md))与一份外部 review(temp/gpt review.md,其五环模型里实体+流水承担 Remember,本系统服务于 Act 的质量)。

事实基础(已核实):仓库内无任何记忆存储;prompt 分层(ADR-0022)的四个 yantao section 是静态「领域纪律」文件,唯一动态注入是每轮现算的能力目录(`agent/pre-step`);唯一的偏好类字段是 person frontmatter 的 `relation`/`email`(邮件分诊在用,本质是待迁移的实体域记忆雏形);提案卡现有七类动作(ADR-0021 六类 + ADR-0029 的 `edit-section`),是人类闸门的既有形态;`kb_*` 工具十一、`yantaoKb` RPC 二十一。

决定:

1. **定义边界:记忆 = 影响 agent 行为方式的规则与偏好(「怎么做」);关于实体的知识(「是什么」)仍落实体本身**(章节/流水),不新造机制。实体知识沉淀缺的不是记忆,而是「提炼时自动总结并提案写入章节」——提炼闭环已在做。Recall/Reason(「这个项目最近发生了什么」)靠流水检索/时间线,是另一条线,不在本 ADR 范围(台账 #3)。
2. **三类作用域**:全局(整个工作台的行事偏好)、能力域(挂在某能力上,触发时注入)、实体域(绑定具体实体的行为规则,如「给此人回信用正式语气」)。实体域与实体章节的分界:章节是结构化产出,实体域记忆是**跨能力触发**的行为规则——任何涉及该实体的任务都注入,而非只在读该实体时可见。person 的 `relation`/`email` 将来可迁移为实体域记忆。
3. **分期:一期只做全局 + 能力域;实体域挂起观察**(台账 #1)——它的准入判据「行为规则而非事实」最难操作,等前两档跑出手感再验证真伪。**首个验证场景是邮件分诊**:处理邮件时纠正 agent → 提案「存为记忆」→ 下次 `kb_run_capability(mail)` 注入。用这一个场景倒推存储格式与注入接口,别的场景等邮件跑通再说。
4. **注入全走动态,不改四个静态 section**:ADR-0022 增补「动态 section」注册概念。全局记忆 → 系统 prompt 的动态 section(模式同能力目录,每轮重算);能力域记忆 → `kb_run_capability` 运行该能力时随运行上下文注入;实体域(二期)→ 实体进入任务上下文时。**价值验收在注入侧**:只写不读的记忆是坟场。
5. **写入闸门:agent 提案 → 提案卡 → 人批准**,不支持免审直写。日常形态:用户在弹窗/对话里纠正 agent(「以后这类邮件直接删」),agent 提一张记忆卡供批;对话兜底是 agent 被纠正时主动提示「要把这条存为记忆吗」。**记忆不参与信任分级降级**(外部 review §4 的分级适用于高频低危操作;记忆低频高杠杆且自我强化——agent 依旧记忆产生新提案,坏记忆滚雪球)。
6. **实现前必须收敛的待决**(记于此防丢):存储位置与格式(候选 `<kbRoot>/.dsh/yantao/memory/`,沿 ADR-0024 修订的簿记区原则);去重与冲突裁决;上限与修剪(删推测只能人);弹窗交互形态(提案卡新动作 vs 独立轻弹窗);工具面(倾向提案卡新动作,零新工具,沿 ADR-0029 先例)。

## 取舍台账——为控制牺牲的便利性

| # | 牺牲 | 换来 | 重开条件 |
|---|---|---|---|
| 1 | 实体域缓发,一期只有全局+能力域 | 准入判据(规则 vs 事实)未经实战检验,宁缺毋滥 | 前两档跑出手感,且出现真实的实体级行为规则需求 |
| 2 | 记忆永不免审,每条一次点击 | 坏记忆不会滚雪球;记忆自我强化,错了代价是之后所有同类行为 | 出现高频记忆写入场景且误写可逆、可批量撤销 |
| 3 | 不与 Recall/Reason 合流 | 本 ADR 范围可控,不重造实体+流水已承担的职责 | 流水检索/时间线成熟后统一评估「记忆要不要参与召回」 |
| 4 | 动态注入而非把记忆写成静态 section | agent 可参与沉淀(静态文件只能人手编) | 无——静态方案违背「agent 参与沉淀」的初衷,不设重开 |
| 5 | 一期不定义记忆的机器可读冲突语义 | 实现不被去重算法绑架 | 同义/矛盾记忆多到人眼维护不过来 |

原因:

- **为什么记忆只管「怎么做」**:存储、写入闸门、注入时机三者都取决于内容的性质——行为规则要在**动作发生前**注入,实体知识在**读写实体时**就在场;混为一谈会把两套时机搅在一起。
- **为什么人批不降级**:审批员疲劳(review §4)的真场景是每天几十张高频低危卡;记忆是低频高杠杆操作,一条坏记忆扭曲的是之后所有同类行为,且 agent 会依据旧记忆产生新提案——自我强化必须有人类断路器。
- **为什么邮件先行**:它是唯一已有完整闭环回路的能力(五拍:人触发→脚本→session 分析→卡→批准),也是原始诉求的原话场景;闭环最短,反馈最快。
- **为什么现在立 ADR 而不急着实现**:外部 review 的最大告诫是「别再囤 ADR,去验证持续使用」——但记忆恰恰是验证的前提设施(没有它,每次纠正都无法累积);立此存照,实现按邮件场景的最小闭环推进。

后果:

- **本 ADR 是设计裁定,不含立即代码改动**。实现开工时的增量(另行提交,届时更新本注记):ADR-0022 增补动态 section 注册;提案卡新增记忆动作类型(或独立轻弹窗,待决 #4);控制器/kb 包的存储与注入增量;`packages/yantao/CONTEXT.md` 增「记忆」词条(随实现)。
- 文档同步(本批):`docs/yantao/README.md` ADR 索引(本条)、`docs/yantao/TODO.md` next 区改指本 ADR、讨论稿 `docs/yantao/memory.md` 保留为本 ADR 的背景材料。
- 零新工具、零新 RPC:`kb_*` 保持十一、`yantaoKb` 保持二十一(工具面待决 #5 若落成提案卡新动作,则连实现期也不破此数)。

落地注记(2026-09-23,待决收敛——决定 6 的五项全部裁定,实现按下述执行):

1. **存储**:`<kbRoot>/.dsh/yantao/memory/` 下 markdown 文件——`global.md`(全局)+ `capabilities/<能力名>.md`(能力域);人可直接看改,符合「文件即真相」;不用 json。实体域(二期)届时增 `entities/` 子目录,本期不定。
2. **去重与冲突**:零算法。提卡时把疑似重复/矛盾的旧记忆并列展示,人裁决(采用/合并/放弃);台账 #5 的立场兑现为「人眼维护,机器不猜」。
3. **上限与修剪**:每作用域软上限(超限注入时按新旧截断并提示);删除只经人——记忆管理视图列出/删除,agent 无删除通道。
4. **交互形态**:提案卡新增 `add-memory` 动作类型,不开独立弹窗;入口两处——邮件面板纠正时(人侧手势,直写无需过卡,人本来就是作者)与会话中被纠正时 agent 提卡(过卡人批)。
5. **工具面**:零新工具、零新 `kb_*`;wire 增量仅限 `yantaoKb` 的记忆 RPC(列表/写入/删除,实现期登记进生成目录);agent 侧沿提炼管线先例,在会话裁决协议中增 `memories[]` 段,由 UI 解析为 `add-memory` 提案行。

实现分四批(沿 ADR-0031 惯例,一批一提交):① 存储层(kb 包读写模型 + 记忆 RPC,同步 controller README 与生成目录);② 注入层(ADR-0022 增补动态 section:全局记忆拼系统 prompt、能力域记忆入 `kb_run_capability` 运行上下文);③ 手势层(提案卡 `add-memory` + 两入口 + 记忆管理视图);④ 邮件闭环端到端验证(纠正一次 → 下次分析生效;验收 = 同类纠正不再重复)。

落地注记二(2026-09-23,批次①完成):kb 包新增 `memory.ts`——行式 markdown 读写模型(条目 id = `sha1("<scope>|<text>")`,删除按 id 定址、陈旧 id 报不存在;解析容忍手改,散行归前导区、空白子弹跳过)与 `MEMORY_SCOPE_SOFT_CAP = 50`。`yantaoKb` 登记三个 RPC:`memoryList`(目录扫描列作用域,global 恒第一,手建文件即作用域)、`memoryAdd`(人侧写入,精确重复拒绝)、`memoryDelete`(人侧删除);均要求已选知识库根。wire 类型已登记生成目录,controller README 同步。

落地注记三(2026-09-23,批次②完成——注入层):**全局记忆**走动态 section `yantao:behavior-memory`(order 150,夹在静态 `yantao:memory` 140 与 `yantao:skills` 160 之间)——`PromptSection.text` 注册为函数 provider,每次组装同步重读 `global.md`,空作用域贡献零文本,`setRoot` 换库即时生效;ADR-0022 以落地注记承认「动态 section」概念,静态四节与决定 6 不动。**能力域记忆**走运行缝隙:`KbCapabilityRunResult` 增可选 `memory` 字段,`runByName` 三条路径(sidecar 指令型/脚本型、中央路由)统一读取 `capabilities/<name>.md` 渲染为运行上下文块(读取失败一律降级为缺席,记忆故障不拦运行);agent 的 `kb_run_capability` render 把记忆块拼在指令正文/运行结果之后,人侧 `capabilityRun` 结果同样携带——邮件面板的 client 驱动分析(批次④)就从结果里取。软上限在注入侧执行:超限保留最新 50 条并注明省略数,文件本身永不裁剪。wire 增量仅此一个可选字段,零新 RPC、零新工具。

落地注记四(2026-09-23,批次③完成——手势层):提案卡增第八类动作 `add-memory`(组键 `group.memory`,排在最后),`ProposalTarget` 相应增必填 `memoryAdd` 缝隙(所有调用方被迫表态);应用时精确重复不算失败,读作「已记得,无需重记」进 skipped。两入口齐备:**邮件面板人侧直写**——分析结果下方一行「作用域 + 一句话 + 记住」,不经卡(人本来就是作者);**会话裁决协议**——`MailAnalysis` 增 `memories[]` 段(prompt 要求只收行为纠正或偏好、每条一句话、写法能脱离这批邮件单独成立),UI 解析为提桧行。一处有意收紧:模型只产出 `text`+`why`,**作用域由 UI 钉死为 `mail`**——模型自选作用域一旦滑成 global 就泄进每个任务,宁可少不可错;放宽留给实体域/能力域二期。**记忆管理视图**落在进料栏新标签「记忆」(会议与能力之间),列全部作用域(global 恒先,能力域显原名)、逐条可删(陈旧 id 刷新列表而不猜)、底部直加行,重复直加同样读作「已记得」。零新工具、零新 RPC(三个记忆 RPC 批次①已登记)。

落地注记五(2026-09-23,批次④完成——邮件闭环接线):client 驱动的分析从此带上邮件域记忆——`fetchMail` 把 `capabilityRun('mail')` 结果里批次②的 `memory` 块原样带回(`MailFetchResult` 增可选 `memory`),`mail-run` 存进状态,`runMailAnalysis`/`MailAnalyser` 增可选 `memory` 参数,`mailPrompt` 把它放在开场之后、知识库清单之前(渲染块自带【行为记忆】头与软上限截断,批次②的注入语义原样复用,零新读取路径)。至此闭环闭合:纠正(面板直写或卡片批准)→ `capabilities/mail.md` → 下次读取的运行结果携带 → 下次分析的 prompt 遵守。全局记忆那条腿早已由批次②的系统 prompt 动态 section 承担,分析会话天然在内。**验收(同类纠正不再重复)属实操验证**:需真实 Outlook 与模型各跑一轮,由人验收,代码侧闭环到此完整。

落地注记六(2026-10-01,写侧权威移交 ADR-0044):记忆的写侧自此由 ADR-0044(提案-批准制)管辖——agent 的唯一写面是新工具 `kb_propose_memory`(只进提案队列,队列**永不注入**),批准入口为会话内批准卡片与记忆视图「待批准」区,UI 面手动运行另有「提炼经验」按钮经 headless 提炼者代笔。决定 5 的闸门(agent 提案 → 人批准,永不免审)原样,变的是提案的载体(提案队列替代提案卡 `add-memory` 的记忆提名位)与批准的界面。`kb_*` 工具十一 → 十三(ADR-0031 执行桥 +1、本批提案工具 +1),`yantaoKb` 增 memoryProposalList/Approve/Discard 三件套。读侧(落地注记三的动态注入)不受影响。
