# yantao 记忆系统设计(讨论稿)

本文是 2026-09-23 记忆设计讨论的纪要,保留作背景材料;**结论已由 [ADR-0032](../adr/0032-behavior-memory.md) 裁定**,以 ADR 为准。

## 1. 定义边界

**记忆 = 影响 agent 行为方式的规则与偏好("怎么做");关于实体的知识("是什么")仍落实体本身**(章节/流水),不新造机制。

- 外部 review(gpt review.md §3)的五环模型里,实体+流水承担 Remember;本记忆系统服务于 **Act 的质量**——让 agent 下次做得更聪明。两者互补不重叠。
- Recall/Reason("这个项目最近发生了什么")靠流水检索/时间线,是另一条线,不混入本轮。
- 实体知识沉淀缺的不是记忆,而是"提炼时自动总结并提案写入对应章节"这一步——提炼闭环(ADR-0029/0030)已在做。

## 2. 作用域分类(三类)

| 作用域 | 内容示例 | 注入时机 |
|---|---|---|
| **全局** | "新建项目应尝试关联 area"、"某些事项不进 area" | 动态 section 拼进系统提示(同能力目录,每轮重算) |
| **能力域** | "处理邮件时,同类邮件直接提示删除" | `kb_run_capability` 运行该能力时随运行上下文注入 |
| **实体域** | "给某人回信用正式语气"(一期缓发) | 任务上下文中出现该实体时注入 |

- 实体域记忆的准入条件从严:必须是**行为规则**而非事实;事实进实体章节。它与实体章节的区别在于**跨能力触发**——任何涉及该实体的任务都注入,而不只在读该实体时可见。
- person 现有的 `relation`/`email` frontmatter 字段是事实上的实体域偏好,将来可迁移成实体域记忆。

## 3. 写入闸门

- **agent 提案 → 提案卡 → 人批准**后落库(与五拍节奏一致);日常形态:用户在弹窗/对话里纠正 agent("以后这类邮件直接删"),agent 提一张记忆卡供批准。
- 对话兜底:agent 被纠正时可主动提示"要把这条存为记忆吗"。
- **不支持免审直写;记忆不参与信任分级降级**(外部 review §4 的分级适用于高频低危操作,记忆低频高杠杆且自我强化——agent 依旧记忆产生新提案,坏记忆会滚雪球,故始终逐条人批)。

## 4. 注入机制

全部走动态注入,不改动 ADR-0022 的四个静态"领域纪律"section;ADR-0022 需增加"动态 section"注册概念:

1. 全局记忆 → 系统 prompt 的动态 section(模式同每轮重算的能力目录);
2. 能力域记忆 → `kb_run_capability` 的运行上下文;
3. 实体域记忆 → 实体进入任务上下文时(二期)。

**记忆的价值验收是注入侧,不是存储侧**:只写不读的记忆是坟场。

## 5. 分期

- **一期:全局 + 能力域**。直接命中邮件场景,闭环最短。
- **二期:实体域**。挂起观察——等前两类跑出手感,验证"行为规则 vs 事实"的准入判据是否真的可操作,再决定做不做。
- **首个验证场景:邮件分诊**。处理邮件时纠正 agent → 弹窗"存为记忆" → 下次 `kb_run_capability(mail)` 注入。用这一个场景倒推存储格式与注入接口,别的场景等邮件跑通再说。

## 6. 下一轮待决(实现前必须收敛)

1. **存储位置与格式** —— 候选 `<kbRoot>/.dsh/yantao/memory/`(与 state.json、templates 同级的簿记区),md 或 json;按 KB 自包含原则(ADR-0024 修订)不放 KB 外。
2. **去重与冲突** —— 新记忆与旧记忆矛盾时的裁决(新压旧?人裁?),同义规则合并。
3. **上限与修剪** —— 记忆条数增长后的治理;谁有资格删(推测:只能人)。
4. **弹窗交互形态** —— "存为记忆"进提案卡(新动作类型)还是独立轻弹窗;纠正发生的入口(邮件面板/对话/能力运行结果)各自怎么长出这个手势。
5. **工具面** —— agent 提案记忆走提案卡新动作即可,还是需要新 `kb_*` 工具;倾向前者(零新工具,沿 ADR-0029 先例)。
